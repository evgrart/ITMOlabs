1. Java-сервлеты. Особенности реализации, ключевые методы, преимущества и недостатки относительно CGI и FastCGI. Контейнеры сервлетов. Жизненный цикл сервлета.

Сервлеты представляют собой Java-классы, которые работают на стороне сервера, принимают запросы от клиентов (обычно браузеров) и генерируют ответы.
Сервлеты выполняются не сами по себе, а внутри специальной среды, называемой контейнером сервлетов (например, Apache Tomcat, Jetty). 
Контейнер управляет жизненным циклом сервлета, который состоит из трех основных фаз. Для каждого типа сервлета контейнер создает только один экземпляр, который затем обрабатывает 
все запросы в отдельных потоках.

Жизненный цикл сервлета:

Инициализация: Когда контейнер получает первый запрос для определенного сервлета (или при старте самого контейнера), он загружает класс сервлета, создает его экземпляр и вызывает метод init() 
только один раз за всю жизнь объекта. В этом методе обычно размещают ресурсоемкий код инициализации, например, установку соединения с базой данных.

Обработка запросов: Каждый входящий клиентский запрос обрабатывается в отдельном потоке. Контейнер вызывает метод service() для каждого запроса, передавая ему объекты ServletRequest (содержит данные запроса) и ServletResponse (для формирования ответа). Метод service() анализирует тип HTTP-запроса (GET, POST и т.д.) и вызывает соответствующий ему метод (doGet(), doPost() и др.).

Уничтожение: Когда контейнер решает удалить сервлет (например, при остановке сервера или перезагрузке приложения), он вызывает метод destroy(). Этот метод также вызывается только один раз и используется для освобождения ресурсов, таких как закрытие соединений с БД.

public void init(ServletConfig config): Вызывается контейнером для инициализации сервлета.

public void service(ServletRequest request, ServletResponse response): Основной метод, получающий все запросы. Он определяет HTTP-метод и вызывает соответствующий doXXX метод. Обычно его не переопределяют напрямую.

protected void doGet(HttpServletRequest request, HttpServletResponse response): Обрабатывает HTTP GET-запросы, которые обычно используются для получения данных.

protected void doPost(HttpServletRequest request, HttpServletResponse response): Обрабатывает HTTP POST-запросы, которые чаще всего используются для отправки данных на сервер (например, из форм).

public void destroy(): Вызывается перед уничтожением экземпляра сервлета для освобождения ресурсов.

Преимущества сервлетов над CGI:

Производительность: Сервлеты значительно быстрее, так как избегают создания процессов для каждого запроса
Надежность: Управление жизненным циклом и ресурсами со стороны контейнера и JVM делает сервлеты более надежными (в CGI нужно самому освобождать ресурсы).
Масштабируемость: Архитектура сервлетов лучше подходит для высоконагруженных приложений.


Преимущества сервлетов над FastCGI:
Более высокий уровень абстракции: Servlet API предоставляет более богатую и амбициозную спецификацию по сравнению с низкоуровневым протоколом FastCGI.

Преимущества FastCGI над сервлетами:
Возможность использовать любой язык программирования и легко заменять компоненты стека (веб-сервер, приложение).
Изоляция: Так как веб-сервер и приложение работают в разных процессах, сбой в приложении с меньшей вероятностью повлияет на работу веб-сервера.


Контейнер сервлетов (или веб-контейнер) — это специальная программа-сервер, которая является средой выполнения для сервлетов.
Управление жизненным циклом: Контейнер отвечает за загрузку класса сервлета, создание его экземпляра, вызов методов инициализации, обработки запросов и уничтожения.
Маршрутизация запросов: Он анализирует URL входящего запроса и определяет, какой именно сервлет должен его обработать, согласно конфигурации веб-приложения (обычно в файле web.xml или с помощью аннотаций).
Управление потоками: Для обеспечения высокой производительности контейнер использует многопоточную модель. Вместо того чтобы создавать новый объект сервлета на каждый запрос, он создает только один экземпляр сервлета и для каждого нового запроса запускает новый поток, который и выполняет код обработки.
Создание объектов запроса и ответа: Перед тем как передать запрос сервлету, контейнер парсит HTTP-запрос и упаковывает всю информацию в удобные Java-объекты (HttpServletRequest). Он также предоставляет объект HttpServletResponse, через который сервлет формирует и отправляет ответ клиенту.

Ленивая инициализация (по умолчанию): Контейнер загружает класс сервлета и создает его экземпляр только тогда, когда приходит первый запрос, предназначенный для этого сервлета.
Предварительная инициализация: Можно настроить контейнер так, чтобы он создавал экземпляр сервлета сразу при старте приложения, не дожидаясь первого запроса. Это полезно, если инициализация сервлета занимает много времени. Это делается с помощью параметра loadOnStartup.

Популярными реализациями контейнеров сервлетов являются Apache Tomcat, Jetty, JBoss и GlassFish.

Сразу после создания экземпляра контейнер вызывает метод init(). Этот метод также вызывается только один раз.
Этот метод предназначен для выполнения одноразовых, потенциально ресурсоемких операций.
Контейнер передает в метод init() объект ServletConfig, который содержит параметры инициализации для данного сервлета.

Каждый раз, когда клиент отправляет запрос, который должен быть обработан этим сервлетом, контейнер выполняет следующие шаги:

Создание нового потока: Для каждого запроса создается отдельный поток. Это позволяет одному экземпляру сервлета одновременно обрабатывать множество клиентских запросов.
Создание объектов request и response: Контейнер создает объекты HttpServletRequest и HttpServletResponse.
Вызов метода service(): Контейнер вызывает метод service() сервлета, передавая ему созданные объекты запроса и ответа.
Метод: protected void service(HttpServletRequest request, HttpServletResponse response)
Назначение: Этот метод является главным диспетчером. Он анализирует тип HTTP-метода (GET, POST, PUT и т.д.) из объекта request и вызывает соответствующий ему обработчик: doGet(), doPost() и так далее. Именно в этих doXXX методах разработчик и пишет основную логику приложения.
Завершение потока: После того как метод service() (и, соответственно, doGet() или doPost()) завершает свою работу, поток, обслуживавший этот запрос, уничтожается. Объект самого сервлета при этом остается в памяти, готовый обслуживать новые запросы в новых потоках.

Когда контейнер решает удалить сервлет (например, при остановке сервера или выгрузке веб-приложения), он вызывает метод destroy().


    Клиент (браузер) отправляет HTTP-запрос на сервер, например: GET /myapp/userinfo HTTP/1.1.

    Веб-сервер (например, Nginx) на сервере принимает этот запрос. Он смотрит на URL и по своим правилам конфигурации понимает, что все запросы, начинающиеся с /myapp/, должны быть обработаны не им, а другим приложением.

    Веб-сервер перенаправляет (проксирует) запрос на Контейнер сервлетов (например, Tomcat), который работает на том же или другом сервере.

    Контейнер сервлетов (Tomcat) получает запрос. Он уже "заточен" под Java. Он анализирует URL, находит веб-приложение myapp и определяет, что путь /userinfo должен обрабатываться конкретным сервлетом (например, UserInfoServlet).

    Контейнер вызывает метод service() (а затем doGet()) у этого сервлета, передавая ему всю информацию из запроса в виде удобных Java-объектов HttpServletRequest и HttpServletResponse.

    Сервлет выполняет свою работу (например, лезет в базу данных), формирует ответ и отдает его обратно Контейнеру.

    Контейнер передает этот ответ Веб-серверу.

    Веб-сервер отправляет финальный HTTP-ответ обратно клиенту (браузеру).


2. Диспетчеризация запросов в сервлетах. Фильтры сервлетов.

Диспетчеризация — это механизм, который позволяет передавать управление обработкой запроса от одного сервлета к другому ресурсу (другому сервлету, JSP-странице или HTML-файлу) внутри сервера. Клиент (браузер) ничего об этой передаче не знает, для него это выглядит как один единственный запрос-ответ.

Ключевой инструмент для этого — интерфейс javax.servlet.RequestDispatcher.
У этого интерфейса есть два основных метода: forward() и include().
request.getRequestDispatcher("/area-check").forward(request, response);


forward() полностью передает управление обработкой запроса другому ресурсу. Исходный сервлет после вызова этого метода больше не может ничего записать в ответ.

Как это работает:

    Сервлет A получает запрос от клиента.

    Он выполняет какую-то логику (например, извлекает данные из БД).

    Сервлет A вызывает request.getRequestDispatcher("/view.jsp").forward(request, response).

    Контейнер передает те же самые объекты request и response ресурсу /view.jsp.

    Теперь /view.jsp отвечает за генерацию всего ответа клиенту.

    Контроль в сервлет A уже не возвращается.


include() временно передает управление другому ресурсу, чтобы включить его вывод в ответ основного сервлета. После того как включенный ресурс отработает, управление возвращается обратно в исходный сервлет.


Фильтр — это объект, который может перехватывать входящие запросы к ресурсу (сервлету, JSP, HTML) и исходящие ответы от него. Фильтры позволяют выполнять сквозную (cross-cutting) функциональность — код, который должен применяться ко многим запросам, не "загрязняя" логику самих сервлетов.
Фильтры выстраиваются в цепочку (FilterChain). Запрос последовательно проходит через все фильтры в цепочке, доходит до целевого сервлета, а затем ответ от сервлета проходит через те же фильтры в обратном порядке.
Аутентификация и авторизация: Проверка, залогинен ли пользователь и есть ли у него права доступа к запрашиваемому ресурсу.
Логирование: Запись информации о каждом запросе (URL, IP-адрес, время обработки).


Фильтр реализует интерфейс javax.servlet.Filter с тремя методами:

init(FilterConfig config): Вызывается контейнером один раз при инициализации фильтра.
destroy(): Вызывается один раз при выгрузке приложения для освобождения ресурсов.
doFilter(ServletRequest request, ServletResponse response, FilterChain chain): Самый главный метод. Вызывается контейнером для каждого запроса, который соответствует маппингу фильтра.
chain.doFilter(request, response) - передача дальше по цепочке;
Настройка в web.xml, filter, filter-mapping
Запрос -> filter1 -> filter2 -> filter3 -> обработка -> filter3 -> ... -> filter1 -> ответ


3. HTTP-сессии - назначение, взаимодействие сервлетов с сессией, способы передачи идентификатора сессии.

HTTP-сессия — это механизм, который позволяет серверу "помнить" информацию о конкретном пользователе между его многочисленными HTTP-запросами. Это способ создать "stateful" (с сохранением состояния) диалог поверх stateless-протокола HTTP.
В Java Servlet API для работы с сессиями предназначен интерфейс javax.servlet.http.HttpSession.
HttpSession session = request.getSession(); 
Объект сессии, по сути, представляет собой хранилище типа "ключ-значение" (`Map`), где можно хранить любые Java-объекты.
session.getAttribute / set
session.getId()
session.getCreationTime()
session.getLastAccessedTime()

Сервер должен как-то передать клиенту тот самый "номерок" (ID сессии) и получать его обратно с каждым запросом. Существует три основных способа.

1. Cookies (Основной и предпочтительный способ)

Это способ по умолчанию.

    Создание сессии: Когда сервлет вызывает request.getSession() в первый раз, контейнер создает сессию и генерирует уникальный ID (например, A1B2C3D4...).

    Отправка Cookie: Контейнер автоматически добавляет в HTTP-ответ заголовок Set-Cookie. Этот cookie обычно называется JSESSIONID и содержит сгенерированный ID.
    Set-Cookie: JSESSIONID=A1B2C3D4...; Path=/myapp

    Возврат Cookie: Браузер, получив такой cookie, автоматически прикрепляет его ко всем последующим запросам на тот же сервер (домен и путь).
    GET /myapp/somepage HTTP/1.1
    Cookie: JSESSIONID=A1B2C3D4...

    Идентификация: Сервер читает JSESSIONID из заголовка Cookie, находит соответствующий объект сессии у себя в памяти и связывает этот запрос с ним.

2. URL Rewriting 
Если браузер не поддерживает или отключил cookies, контейнер может использовать этот механизм как запасной. ID сессии добавляется прямо в URL в виде параметра.
response.encodeURL

4. Контекст сервлета - назначение, способы взаимодействия сервлетов с контекстом.
ServletContext — это один из ключевых объектов в Java Web, который представляет собой "глобальную среду" для всего веб-приложения.

ServletContext создается контейнером сервлетов в единственном экземпляре в момент запуска (развертывания) вашего веб-приложения и уничтожается только при его остановке. Все сервлеты, фильтры и слушатели внутри одного веб-приложения делят между собой один и тот же объект ServletContext.
    
Общее хранилище данных (Application Scope): Контекст предоставляет "область видимости приложения" — место для хранения объектов, которые должны быть доступны абсолютно всем компонентам приложения (сервлетам, JSP, фильтрам) и на протяжении всей жизни приложения.

Доступ к параметрам инициализации приложения: В файле web.xml можно определить глобальные параметры для всего приложения (например, email администратора, путь к файлу конфигурации, ключи API). ServletContext позволяет любому сервлету прочитать эти параметры.

Доступ к ресурсам веб-приложения: Через контекст можно получить доступ к файлам, находящимся внутри веб-приложения (внутри WAR-файла), например, к шаблонам, файлам свойств или статическим данным. 

Взаимодействие с контейнером сервлетов: Контекст предоставляет информацию о самом сервере и приложении, например, версию Servlet API, название сервера, MIME-типы файлов.

Логирование: Предоставляет простой механизм для записи сообщений в лог-файл сервера.

ServletContext context = getServletContext();

context.setAttribute(String name, Object object): Сохранить объект в контексте.

context.getAttribute(String name): Получить объект из контекста.

context.removeAttribute(String name): Удалить объект.

context.getInitParameter - получить переменную контекста (указываем в web.xml,  <context-param>)


5. JavaServer Pages. Особенности, преимущества и недостатки по сравнению с сервлетами, область применения.

JavaServer Pages (JSP) — это технология Java, позволяющая разработчикам создавать динамический веб-контент (HTML, XML, JSON и т.д.) с помощью шаблонного подхода. В отличие от сервлетов, где вы пишете Java-код, который генерирует HTML, в JSP вы пишете HTML-код и вставляете в него фрагменты Java-кода для динамических частей.

Самая важная концепция: любая JSP-страница при первом обращении к ней транслируется (компилируется) в обычный Java-сервлет контейнером сервлетов.
Скриплеты (<% ... %>): Фрагменты чистого Java-кода. 
Выражения (<%= ... %>): Вычисляют Java-выражение и вставляют его результат в HTML как строку.

Model (Модель): Это данные. Простые Java-объекты, которые содержат информацию для отображения (например, объект User с полями name и email, или List<Product>). Модель ничего не знает о том, как она будет отображаться.

Controller (Контроллер): Это "мозг" операции. Его роль выполняет сервлет.

Он принимает входящий HTTP-запрос.

Обращается к бизнес-логике (например, к сервисному слою) для получения или изменения данных (Модели).

Выбирает, какое Представление (какую JSP-страницу) нужно показать пользователю.

Помещает Модель в request и передает управление JSP.

View (Представление): Это "лицо" приложения. Его роль выполняет JSP-страница.

Ее единственная задача — отобразить данные (Модель), которые ей передал Контроллер.

Она должна быть максимально "глупой" — не содержать бизнес-логики, обращений к базам данных и т.д.

Она использует JSTL и Expression Language (${...}) для доступа к данным и их форматирования.

<jsp:forward page="other.jsp" /> — серверное перенаправление запроса (аналог RequestDispatcher.forward()).

<jsp:include page="menu.jsp" /> — динамическое включение вывода другой страницы

6. Жизненный цикл JSP.

Фаза трансляции и компиляции: Происходит только один раз (или когда JSP-файл изменяется).
Фаза обработки запросов: Стандартный жизненный цикл получившегося сервлета.

Контейнер читает ваш .jsp файл и транслирует его в исходный код Java-сервлета (.java файл). 

    Весь статический HTML-код превращается в Java-команды out.println("...");.

    JSP-выражения <%= ... %> превращаются в out.print(...);.

    JSP-скриплеты <% ... %> просто копируются как есть в метод сервлета.

    Директивы <%@ ... %> используются для генерации правильных импортов и настроек в Java-файле.

    JSP-действия <jsp:...> и теги JSTL превращаются в вызовы соответствующих Java-классов.

Контейнер берет только что сгенерированный .java файл и компилирует его с помощью стандартного Java-компилятора (javac) в байт-код (.class файл).
После того как .class файл готов, контейнер обращается с ним как с обычным сервлетом.
jspInit()
Для каждого нового запроса к hello.jsp контейнер выполняет следующие действия:

    Создает новый поток (thread).

    В этом потоке вызывает метод _jspService(request, response) у того самого единственного экземпляра сервлета.

    _jspService() — это аналог метода service() у сервлетов.

7. Структура JSP-страницы. Комментарии, директивы, объявления, скриптлеты и выражения.

Объявления (Declarations)
Синтаксис: <%! ... %>
Назначение: Код внутри тега объявления помещается на уровень класса сгенерированного сервлета. Это позволяет объявлять переменные экземпляра (поля) и методы, которые будут доступны для всей JSP-страни

Скриптлеты (Scriptlets)
Синтаксис: <% ... %>
Назначение: Фрагменты Java-кода, которые вставляются непосредственно в метод _jspService() сгенерированного сервлета. Это место, где исторически размещалась основная бизнес-логика.

Выражения (Expressions)
Синтаксис: <%= ... %>
Назначение: Это краткая запись для out.print(...). Выражение внутри тега вычисляется, результат преобразуется в строку и вставляется прямо в HTML-вывод.


8. Правила записи Java-кода внутри JSP. Стандартные переменные, доступные в скриптлетах и выражениях.

Объявления (<%! ... %>)
Куда попадает код: В тело класса сгенерированного сервлета.
Здесь можно объявлять поля (переменные экземпляра) и методы.

Скриптлеты (<% ... %>)
Куда попадает код: Внутрь метода _jspService(request, response) сгенерированного сервлета.
Здесь можно писать любые Java-операторы, которые допустимы внутри метода: объявлять локальные переменные, создавать циклы (for, while), условные операторы (if/else), вызывать методы и т.д.
Весь код из всех скриптлетов на странице и статический HTML между ними собирается в один последовательный блок кода внутри _jspService.

Выражения (<%= ... %>)
Куда попадает код: Превращается в out.print(...) внутри метода _jspService.
Внутри тега должно находиться одно единственное Java-выражение, которое возвращает результат.
Результат выражения автоматически преобразуется в String и выводится в HTML.
Нельзя ставить точку с запятой (;) внутри этого тега.
Нельзя писать сюда полноценные операторы 


9. Bean-компоненты и их использование в JSP.

Bean-компоненты (JavaBeans) — это фундаментальная концепция в экосистеме Java, которая играет ключевую роль в построении хорошо структурированных JSP-приложений. Они являются "Моделью" в паттерне MVC.
JavaBean — это обычный Java-объект, который следует определенному набору соглашений. Эти правила позволяют фреймворкам и инструментам (таким как JSP-контейнер) автоматически работать с этим объектом: создавать его, читать его свойства и записывать в них значения.

1. Публичный конструктор без аргументов
2. Приватные поля
3. Публичные методы

<jsp:useBean>
Этот тег — самый главный. Он объявляет и создает экземпляр bean-компонента.

Синтаксис: <jsp:useBean id="beanName" class="com.example.ClassName" scope="scopeName" />

id: Имя переменной, через которую вы будете обращаться к bean-компоненту на JSP-странице.
class: Полное имя Java-класса (включая пакет) для bean-компонента.
scope: Область видимости, где будет храниться этот bean. Определяет его жизненный цикл (page, app, request, response).

<jsp:setProperty> (если есть сеттер и геттер)

Этот тег устанавливает значение свойства у ранее созданного bean-компонента.
Синтаксис: <jsp:setProperty name="beanName" property="propertyName" value="someValue" />

<jsp:getProperty>
Этот тег получает значение свойства у bean-компонента и выводит его в HTML.


10. Стандартные теги JSP. Использование Expression Language (EL) в JSP.

Чтобы использовать JSTL, нужно:
Убедиться, что в вашем проекте есть .jar-файл с JSTL (например, jstl-1.2.jar). В современных серверах приложений, таких как Tomcat, он часто уже включен.
Подключить нужную библиотеку тегов на JSP-странице с помощью директивы <%@ taglib %>.

Библиотека Core (prefix="c")
<c:out> — безопасный вывод данных
<c:set> — создание и установка переменных
<c:if> — условный оператор
Выполняет свое тело, если условие истинно. Нет else, для альтернативной ветки нужен второй <c:if> с противоположным условием.

<c:choose>, <c:when>, <c:otherwise> — аналог switch

<c:forEach> — итерация по коллекциям и массивам

Есть еще библиотеки Formatting, Functions

Expression Language (EL) — это язык выражений, созданный для легкого доступа к данным (JavaBeans, коллекциям, параметрам) из JSP без использования Java-кода. EL — это то, что вы пишете внутри ${...}.
Простой синтаксис: ${выражение}.

Доступ к свойствам JavaBeans: Используется оператор . (точка).
${user.name} автоматически транслируется в вызов user.getName(). Это работает, потому что user — это JavaBean.

13. Архитектура веб-приложений. Шаблон MVC. Архитектурные модели Model 1 и Model 2 и их реализация на платформе Java EE.

MVC — это не технология, а концепция, архитектурный шаблон, который предлагает разделить приложение на три основных компонента:

    Model (Модель):

        Что это? Данные и бизнес-логика.

        Отвечает на вопросы: "Какие данные у нас есть?" (сущности типа User, Product) и "Что мы можем с ними делать?" (бизнес-правила, например, "скидка не может быть больше 50%").

        Реализация в Java: Простые Java-объекты (JavaBeans/POJO), сервисные классы (Service Layer), классы доступа к данным (DAO).

        Важно: Модель ничего не знает о том, как она будет отображаться. Она не содержит HTML или информации о HTTP-запросах.

    View (Представление):

        Что это? Пользовательский интерфейс.

        Отвечает на вопрос: "Как показать данные пользователю?".

        Реализация в Java EE: JSP-страницы, которые используют JSTL и EL для рендеринга HTML.

        Важно: Представление должно быть максимально "глупым". Его единственная задача — отобразить данные, которые ему передали. Оно не должно содержать бизнес-логику.

    Controller (Контроллер):

        Что это? "Диспетчер" или "посредник" между пользователем, Моделью и Представлением.

        Отвечает на вопрос: "Что делать с запросом пользователя?".

        Реализация в Java EE: Сервлеты.

        Важно: Контроллер не содержит бизнес-логики и не генерирует HTML. Он только координирует работу: принимает запрос, вызывает нужные методы у Модели, выбирает подходящее Представление и передает ему данные.

Как фильтры участвуют в цепочке? Разница между doFilter() и передачей управления.
Фильтры образуют цепочку, через которую последовательно проходит запрос, прежде чем попасть в сервлет, и через которую проходит ответ в обратном порядке. Порядок фильтров определяется их маппингом в web.xml.
doFilter(request, response, chain) — это основной метод самого фильтра, его "точка входа". Внутри этого метода вы пишете свою логику (проверку, логирование, модификацию).
chain.doFilter(request, response) — это вызов внутри вашего метода, который передает управление следующему элементу цепочки (следующему фильтру или, если фильтров больше нет, целевому сервлету).
Если фильтр не вызывает chain.doFilter(), он разрывает цепочку. Запрос дальше не пойдет, и сервлет никогда не будет вызван. 


Чем отличается HttpSession от ServletContext?
HttpSession:
Область видимости: Сессия пользователя. Данные привязаны к одному конкретному пользователю.
Время жизни: Начинается с первого визита пользователя и заканчивается, когда он закрывает браузер, истекает таймаут
Экземпляры: Свой для каждого клиента.
ServletContext:
Область видимости: Приложение. Данные являются глобальными для всех пользователей и компонентов приложения.
Время жизни: Начинается при старте веб-приложения и заканчивается при его остановке.
Экземпляры: Один-единственный на все веб-приложение.


Опишите структуру .war-файла.
.war (Web Application Archive) — это просто .zip-архив со стандартной структурой каталогов, используемый для развёртывания веб-приложений на Java EE серверах.
Корень (/): Место для общедоступных ресурсов (HTML, JSP, CSS, JS, картинки), к которым можно обратиться напрямую из браузера.
/WEB-INF/: Приватный каталог. Ресурсы внутри него недоступны для прямого обращения из браузера. 
web.xml: Дескриптор развёртывания. Центральный конфигурационный файл, где описываются сервлеты, фильтры, слушатели, страницы ошибок, параметры контекста и т.д.
/WEB-INF/classes/: Сюда помещаются скомпилированные .class-файлы вашего проекта (сервлеты, модели, DAO и т.д.) с сохранением структуры пакетов.
/WEB-INF/lib/: Сюда кладутся все сторонние библиотеки (.jar-файлы), от которых зависит ваше приложение (драйверы БД, JSTL, Spring и т.д.).


Разница между <%@ page %>, <%@ include %> и <jsp:include>.

<%@ page %> - задает атрибуты для всей JSP-страницы (импорты, кодировка и т.д.).
<%@ include %> - содержимое включаемого файла текстуально вставляется в основную JSP перед ее компиляцией в один большой сервлет.
<jsp:include> - управление динамически передается другому ресурсу (JSP/сервлету). Его результат включается в ответ основной страницы.
