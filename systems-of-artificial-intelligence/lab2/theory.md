# Теория к лабораторной №2 и ответы для защиты

Примеры относятся к нашей учебной базе Warhammer 40K. Код системы находится в [main.pl](main.pl), факты и правила — в [базе первой лабораторной](../lab1/knowledge_base.pl), онтология — в [ontology.owl](../lab1/ontology.owl). Подробный разбор первой лабораторной остался в [lab1/theory.md](../lab1/theory.md).

## 1. В чём суть второй лабораторной

Мы сделали **систему поддержки принятия решений (СППР)**: пользователь задаёт предпочтения, а программа помогает выбрать подходящего персонажа и объясняет выбор.

В первой лабораторной мы описали знания о предметной области. Во второй применяем эти знания для решения задачи подбора.

```text
Ответы пользователя
        ↓
Разбор и проверка ввода
        ↓
Нормализованные ограничения
        ↓
Логический запрос к базе lab1
        ↓
Поиск всех подходящих персонажей
        ↓
Удаление повторов и сортировка
        ↓
Рекомендации с объяснениями
```

Это система на фактах и правилах. Здесь нет обучения нейросети, вероятностной модели или подбора по похожим пользователям. Слово «интеллектуальная» относится к использованию представленных знаний и логического вывода.

Вторая лабораторная подключает именно Prolog-базу через:

```prolog
:- use_module('../lab1/knowledge_base').
```

Файл OWL во время работы `main.pl` не читается. Он представляет предметную область в другом формализме и нужен для онтологической части первой лабораторной.

## 2. Что появилось нового

| Понятие | Что означает | Как реализовано у нас |
| --- | --- | --- |
| СППР | Программа помогает принять решение по заданным условиям | Подбор персонажа |
| Система на основе знаний | Решение строится по явно записанным знаниям | Факты и правила из lab1 |
| Парсинг | Разбор текста на ожидаемые части | Сторона и роль из строки |
| Нормализация | Приведение разных написаний к одному виду | «Хаос» → `chaos`, «командир» → `commander` |
| Валидация | Проверка допустимости данных | Рейтинг — целое от 0 до 10 |
| Ограничения | Требования, которым должен соответствовать результат | Сторона, роль, рейтинг, союзник |
| Построение запроса | Преобразование условий в исполняемый Prolog-терм | `build_query/3` |
| Ранжирование | Упорядочивание подходящих вариантов | Сначала больший рейтинг, затем атом имени |
| Объяснение | Показ причин выбора или отказа | Выполненные и нарушенные условия |
| Диалог | Уточнение запроса через последовательность вопросов | Предпочтения → рейтинг → союзник |

### Парсинг и нормализация на примере

Ввод:

```text
Сторона: Хаос; роль: псайкер
```

После `parse_profile/2`:

```prolog
profile{sides:[chaos], role:psyker}
```

После уточнений «рейтинг 8» и «без союзника» получается:

```prolog
request{sides:[chaos], role:psyker, min_rating:8, ally:none}
```

Это **словарь SWI-Prolog**, то есть структура с именованными полями. `Request.role` обращается к полю `role`.

Наш парсер понимает фиксированный формат и перечисленные варианты. Произвольную фразу вроде «посоветуй кого-нибудь сильного» он не разбирает. Текст пользователя не исполняется как Prolog-код: из разрешённых значений программа сама строит запрос.

### Фильтрация и ранжирование — разные этапы

Фильтрация отвечает: **кто выполнил все обязательные условия?**

Ранжирование отвечает: **в каком порядке показать найденных?**

Если персонаж не подходит по роли, высокий рейтинг его не спасает. Среди подходящих персонажей первым будет вариант с большим рейтингом. При равном рейтинге сравниваются внутренние атомы имён, а не русские подписи.

Рейтинг угрозы и отношения союзничества взяты из учебной модели lab1. Это не официальные параметры настольной игры.

## 3. Пример полного решения и логического вывода

Пользователь выбирает Хаос, псайкера, рейтинг от 8, без ограничения по союзнику.

По смыслу система выполняет:

```prolog
character(C),
chaos_character(C),
psyker(C),
threat_rating(C, R),
R >= 8.
```

Результат: `C = ahriman`, `R = 8`.

Почему Ариман относится к Хаосу? В базе есть:

```prolog
character(ahriman).
belongs_to(ahriman, thousand_sons).
chaos_faction(thousand_sons).
```

И правило:

```prolog
chaos_character(C) :-
    character(C),
    belongs_to(C, F),
    chaos_faction(F).
```

Prolog подставляет `C = ahriman`, находит `F = thousand_sons` и проверяет категорию фракции. Затем проверяет `psyker(ahriman)` и рейтинг.

Это пример **логического вывода**: принадлежность персонажа к стороне получается из других знаний.

**Унификация** — согласование термов с подбором значений переменных. Например, `belongs_to(ahriman, F)` согласуется с фактом `belongs_to(ahriman, thousand_sons)`, поэтому `F = thousand_sons`.

**Поиск с возвратом, или backtracking**, позволяет после одного решения пробовать другие подходящие факты и правила. Так Prolog может перебрать всех персонажей. В интерактивной консоли `;` после найденного ответа запрашивает следующее решение; внутри запроса `;` означает «ИЛИ».

Наша программа применяет правила для доказательства заданной цели. Она не добавляет все возможные выводы в файл базы.

## 4. И, ИЛИ, НЕ: пересечение, объединение и разность

Для этих примеров открой интерактивный Prolog из папки lab2:

```powershell
swipl -q -l ../lab1/knowledge_base.pl
```

Вводи запросы с точкой в конце. Обозначение приглашения `?-` копировать не нужно.

### И — пересечение

```prolog
setof(C, (psyker(C), commander(C)), L).
```

Результат:

```prolog
L = [ahriman].
```

Запятая требует выполнения обоих условий: персонаж должен быть и псайкером, и военачальником.

### ИЛИ — объединение

```prolog
setof(C, (psyker(C); commander(C)), L).
```

Результат:

```prolog
L = [abaddon, ahriman, eldrad_ulthran, imotekh, mephiston, roboute_guilliman].
```

Достаточно хотя бы одного признака. Ариман подходит по обоим, но `setof/3` оставляет его в списке один раз.

### НЕ — исключение из выбранного множества

```prolog
setof(C, (character(C), \+ psyker(C)), L).
```

Результат:

```prolog
L = [abaddon, imotekh, roboute_guilliman].
```

Сначала выбирается конкретный известный персонаж, затем проверяется отсутствие доказательства `psyker(C)`.

**Порядок важен.** Запрос `\+ psyker(C)` с несвязанной переменной не перечисляет всех непсайкеров: он проверяет, можно ли найти хоть какого-нибудь псайкера. Такой персонаж в базе есть, поэтому проверка завершается неудачей.

В нашей базе список псайкеров считается полным для шести описанных персонажей. Только в рамках этого допущения отсутствие признака используется как «не псайкер».

### Сложный запрос с И, ИЛИ и НЕ одновременно

«Найти опасного персонажа Хаоса или ксеносов, который не псайкер»:

```prolog
setof(C,
      ((chaos_character(C); xenos_character(C)),
       dangerous(C),
       \+ psyker(C)),
      L).
```

Результат:

```prolog
L = [abaddon, imotekh].
```

Скобки объединяют две стороны в одно условие. Затем к нему через И добавляются опасность и исключение псайкеров.

Такой выбор доступен и через диалог:

```text
Сторона: Хаос, ксеносы; роль: не псайкер
```

При минимальном рейтинге 8 и без союзника программа покажет Абаддона, затем Имотеха.

Смысл управляющих операторов `,`, `;` и `\+` описан в [документации SWI-Prolog](https://www.swi-prolog.org/pldoc/man?section=control).

### Построение запроса как данных

Упрощённый пример:

```prolog
Goal = (character(C), psyker(C)),
call(Goal).
```

Первая строка создаёт терм и связывает его с `Goal`. Вторая выполняет этот терм как цель. Именно так `build_query/3` передаёт построенное условие механизму поиска.

`true` в построенной цели означает «это условие выполнено без дополнительных требований». Например, выбор «любая роль» превращается в `true`, а не в фильтр по признаку.

### =, ==, is и сравнения — не одно и то же

```prolog
X = ahriman.       % Унификация: X получает значение ahriman.
X == ahriman.      % Проверка тождественности; сама X не связывает.
N is -8.           % Вычисление арифметического выражения справа.
8 >= 7.            % Арифметическая проверка.
```

Строки выше — отдельные примеры. Во втором примере, если `X` ещё не связана, результат будет `false`. У `is` и арифметических сравнений выражения, которые нужно вычислить, должны иметь числовые значения.

### Почему сначала findall, а потом sort

Один персонаж может иметь несколько доказательств соответствия запросу. Например, Ариман одновременно псайкер и военачальник, поэтому условие «псайкер ИЛИ военачальник» находит его двумя путями.

`findall/3` собирает результаты с возможными повторами. `sort/2` удаляет повторы. Затем система отдельно сортирует карточки по рейтингу.

`setof/3` из примеров тоже сортирует и удаляет повторы, но при отсутствии решений завершается неудачей, а не возвращает `[]`. У `setof/3` также есть группировка по свободным переменным цели; в приведённых выше запросах таких дополнительных переменных нет.

## 6. Как обрабатываются ошибки и отсутствие результата

Неизвестная сторона, неверный формат или рейтинг вне 0..10 вызывают сообщение об ошибке и повтор только текущего вопроса.

Явная роль «псайкер и не псайкер» отклоняется как противоречивая.

**Отсутствие подходящего персонажа не обязательно означает логическое противоречие.** Например, требование «Империум, псайкер, рейтинг от 8» осмысленно, но в нашей базе ему никто не соответствует: Мефистон — псайкер Империума с рейтингом 7.

При пустом результате система показывает до трёх отклонённых вариантов и причины. Сначала учитывает число нарушенных условий, затем предпочитает совпадение стороны, потом роли, затем больший рейтинг и имя.

Это диагностика, а не скрытое изменение запроса. Отклонённый вариант не объявляется подходящим.

Упрощённое объяснение отказа:

```text
Мефистон: учебный рейтинг 7 меньше порога 8.
```

Объяснение строится по проверенным признакам и условиям. Программа не генерирует свободное рассуждение и не выводит пользователю полное дерево доказательства.

## 7. Ответы на твои вопросы из первой лабораторной

### 1) Что такое семантическая сеть?

Это представление знаний в виде графа: узлы обозначают понятия или объекты, подписанные связи — отношения между ними.

Фрагмент нашей предметной области:

```text
[ahriman] ──belongsTo──> [thousand_sons]
    │                         │
    │ rdf:type                │ rdf:type
    ↓                         ↓
 [Psyker]                [ChaosFaction]
    │                         │
    │ subClassOf              │ subClassOf
    ↓                         ↓
[Character]                [Faction]
```

Сеть позволяет увидеть, какие сущности связаны и как. Конкретные правила смысла связей зависят от выбранного языка представления.

### 2) Что такое онтология и из чего она состоит?

Онтология — формальное описание понятий предметной области, отношений и ограничений, которое может обрабатываться программами.

У нас это `lab1/ontology.owl`:

| Составляющая | Пример из нашего файла |
| --- | --- |
| Классы — категории объектов | Character, Faction, Psyker, Commander |
| Индивиды — конкретные объекты | ahriman, abaddon, thousand_sons |
| Объектные свойства — связи объектов | belongsTo, allyOf, enemyOf |
| Свойства данных — значения | threatRating: число 8 |
| Иерархия классов | Psyker является подклассом Character |
| Аксиомы и ограничения | Character и Faction несовместимы; у Character ровно одна фракция и один рейтинг |
| Определения классов | ChaosCharacter определяется через принадлежность фракции ChaosFaction |

Классы `Psyker` и `Commander` совместимы: Ариман принадлежит обоим.

В файле также записаны SWRL-правила для союзников и врагов. SWRL — отдельный язык правил, используемый вместе с OWL; это не обязательная составляющая любой онтологии.

Основные понятия языка описаны в [OWL 2 Primer от W3C](https://www.w3.org/TR/owl2-primer/).

### 3) Что такое онтограф?

В общем употреблении так могут называть графическое представление онтологии. В нашей работе **OntoGraf** — конкретная вкладка-плагин Protégé для просмотра классов, объектов и связей.

То есть в контексте защиты:

> Онтология хранит формальные знания, а OntoGraf помогает показать их графически и переходить по связям.

Само изображение не заменяет все аксиомы файла. Например, ограничение количества значений удобнее проверять в описании класса, а не только на графе.

Включение вкладки: `Window → Tabs → OntoGraf`. Возможности описаны на [официальной странице плагина](https://protegewiki.stanford.edu/wiki/OntoGraf).

### 4) Чем отличаются семантическая сеть, онтология и OntoGraf?

| Что | Основная роль | Пример у нас |
| --- | --- | --- |
| Семантическая сеть | Представить знания через узлы и подписанные связи | Ариман → принадлежит → Тысяча Сынов |
| Онтология | Формально задать понятия, отношения и аксиомы | Character, belongsTo, ограничения и определения в OWL |
| OntoGraf | Визуализировать онтологию в редакторе | Граф во вкладке Protégé |

Это связанные понятия, а не три взаимоисключающих формата. Онтологию можно представить графом, а OntoGraf показывает выбранную часть этого представления.

### 5) Что такое триплет и из чего он состоит?

**RDF-триплет = субъект + предикат + объект.**

- Субъект: о чём утверждение.
- Предикат: какое отношение или свойство.
- Объект: с чем связано или какое значение имеет.

Пример:

```text
ahriman | belongsTo | thousand_sons
```

Читается: «Ариман принадлежит Тысяче Сынов».

Те же утверждения в Turtle — компактной записи RDF:

```turtle
@prefix wh: <https://example.org/itmo/wh40k#> .
@prefix rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

wh:ahriman wh:belongsTo wh:thousand_sons .
wh:ahriman rdf:type wh:Psyker .
wh:ahriman rdf:type wh:Commander .
wh:ahriman wh:threatRating "8"^^xsd:integer .
wh:Psyker rdfs:subClassOf wh:Character .
```

Здесь `wh:` сокращает общий IRI-префикс. `rdf:type` задаёт принадлежность классу, `rdfs:subClassOf` — отношение подкласса, `"8"^^xsd:integer` — целочисленный литерал.

В RDF субъект — IRI или пустой узел, предикат — IRI, объект — IRI, пустой узел или литерал. RDF-граф является множеством триплетов. См. [стандарт RDF 1.1](https://www.w3.org/TR/rdf11-concepts/).

Не путай RDF-триплет с количеством аргументов Prolog:

```prolog
belongs_to(ahriman, thousand_sons).
```

Здесь **два аргумента**, а имя предиката задаёт отношение. По смыслу это соответствует тройке «субъект — отношение — объект», но сам синтаксис является Prolog, а не RDF.

### 6) Что такое база знаний?

База знаний — организованные утверждения о предметной области, используемые для получения ответов и новых выводов.

В нашей Prolog-базе есть:

- **Факты:** `psyker(ahriman).` — явно записанное знание.
- **Правила:** `chaos_character(C) :- ...` — способ вывести знание.
- **Запросы:** `chaos_character(ahriman).` — вопрос к базе.

В lab1 записаны **25 одноаргументных фактов, 15 двухаргументных фактов и 7 правил**.

Механизм вывода — отдельная часть системы: SWI-Prolog использует факты и правила, чтобы доказать цель. Текст запроса и ответы не обязаны храниться в файле базы.

Отличие от обычного набора данных в нашей работе: мы записали не только объекты и значения, но и явные правила вывода. Например, сторону Аримана получаем через фракцию, а не дублируем отдельным фактом для каждого персонажа.

Нельзя утверждать, что базы данных вообще не умеют выводить связанные результаты: SQL-запросы, представления и ограничения тоже позволяют работать с отношениями. Здесь акцент именно на логическом представлении знаний.

## 8. Пересечения и объединения в онтологии

В Prolog мы записываем цели, а в OWL можем задавать выражения классов. В Protégé во вкладке DL Query используется Manchester Syntax.

| Операция | Выражение классов | Смысл |
| --- | --- | --- |
| Пересечение | `Psyker and Commander` | Псайкер и военачальник |
| Объединение | `Psyker or Commander` | Хотя бы один из признаков |
| Исключение | `Character and not Psyker` | Персонаж, для которого обоснована непринадлежность Psyker |
| Связь с категорией | `Character and (belongsTo some ChaosFaction)` | Есть принадлежность хотя бы одной фракции Хаоса |
| Связь с объектом | `Character and (belongsTo value thousand_sons)` | Принадлежит конкретно Тысяче Сынов |

Для показа экземпляров выражения сначала запускают reasoner, например HermiT, затем выполняют DL Query с отображением Instances. Это запросы Protégé, их нельзя вставлять в консоль Prolog.

В нашей онтологии:

- Пересечение `Psyker and Commander` даёт Аримана.
- Объединение `Psyker or Commander` охватывает всех шестерых.
- `Character and not Psyker` даёт Абаддона, Имотеха и Жиллимана благодаря явно заданной отрицательной информации об этих объектах.

### Почему НЕ в OWL отличается от \+ в Prolog

Prolog `\+ Goal` успешен, если текущий поиск не смог доказать `Goal`. Это **отрицание как неудача**.

OWL использует **предположение открытого мира**: отсутствие сведений о принадлежности классу не означает непринадлежности ему. Для `not Psyker` нужны основания: например, явно заданная принадлежность дополнению класса или соответствующая несовместимость классов.

Если просто добавить нового персонажа без информации о псайкерстве, OWL не обязан считать его непсайкером. В Prolog `character(C), \+ psyker(C)` включит его в ответ при отсутствии доказательства `psyker(C)`. Тогда нужно пересмотреть наше допущение о полноте списка.
