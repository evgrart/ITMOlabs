\section{Цель работы}

Цель лабораторной работы — реализовать мониторинг веб-приложения из лабораторной работы №3 с помощью JMX, проверить разработанные MBean в JConsole, выполнить мониторинг и профилирование приложения в VisualVM, а также найти и устранить проблему производительности.

\section{Техническое задание}

Для программы из лабораторной работы №3 необходимо реализовать:
\begin{itemize}
    \item MBean, считающий общее число установленных пользователем точек и число точек, не попавших в область. При достижении количества точек, кратного 10, MBean должен отправлять уведомление;
    \item MBean, определяющий площадь получившейся фигуры;
    \item мониторинг разработанных MBean с помощью JConsole;
    \item определение времени, прошедшего с момента запуска виртуальной машины;
    \item мониторинг и профилирование приложения с помощью VisualVM;
    \item определение класса, экземпляры которого занимают наибольший объём памяти, и устранение выявленной проблемы производительности.
\end{itemize}

Отчёт должен содержать исходный код разработанных MBean и сопутствующих классов, результаты мониторинга JConsole, результаты мониторинга и профилирования VisualVM, описание найденной проблемы, способ её локализации и результат исправления.

\section{Порядок выполнения работы}

В приложении реализованы два стандартных MBean. \texttt{PointStatistics} хранит статистику проверенных точек и отправляет JMX-уведомление после каждой десятой точки. \texttt{Area} вычисляет площадь области по текущему значению радиуса.

MBean регистрируются в платформенном MBeanServer при запуске веб-приложения. При остановке приложения они снимаются с регистрации. Для подключения используется локальный процесс Java-сервера, в котором развёрнуто приложение.

\section{Подключение к JVM для мониторинга}

При локальном запуске приложение и инструменты JDK работают на одном компьютере. В JConsole в этом случае выбирается локальный процесс Java-сервера. В VisualVM для построения графика пользовательских MBean необходимо установить плагин \texttt{VisualVM-MBeans}, затем выбрать пункт \texttt{File > Add JMX Connection} и подключиться к процессу.

При удалённом мониторинге WildFly необходимо открыть management-порт сервера и настроить JMX-подключение. Для учебного стенда может использоваться отдельный порт, например:

\begin{lstlisting}[style=textstyle,caption={Пример параметров запуска удалённого JMX}]
-Dcom.sun.management.jmxremote
-Dcom.sun.management.jmxremote.authenticate=false
-Dcom.sun.management.jmxremote.ssl=false
-Dcom.sun.management.jmxremote.port=7203
-Dcom.sun.management.jmxremote.rmi.port=7203
-Djava.rmi.server.hostname=0.0.0.0
\end{lstlisting}

В реальной эксплуатации отключать аутентификацию и SSL нельзя. После проброса порта в JConsole и VisualVM указывается JMX-адрес сервера и, если включена защита, учётные данные пользователя WildFly. В VisualVM удалённое подключение выполняется через \texttt{File > Add JMX Connection}, а не через обычный пункт добавления удалённого хоста.

\section{Расчёт площади области}

В лабораторной работе №3 область состоит из трёх частей:
\begin{itemize}
    \item прямоугольника в четвёртой четверти с шириной $r$ и высотой $r/2$;
    \item четверти круга во второй четверти с радиусом $r/2$;
    \item треугольника в третьей четверти с катетами $r$ и $r/2$.
\end{itemize}

Площади частей равны:
\begin{equation*}
    S_1=\frac{r^2}{2}, \qquad
    S_2=\frac{\pi r^2}{16}, \qquad
    S_3=\frac{r^2}{4}.
\end{equation*}

Итоговая площадь:
\begin{equation*}
    S=S_1+S_2+S_3
     =r^2\left(0.75+\frac{\pi}{16}\right).
\end{equation*}

Например, для $r=1.5$:
\begin{equation*}
    S=1.5^2\left(0.75+\frac{\pi}{16}\right)\approx 2.129286.
\end{equation*}

Для $r=2$:
\begin{equation*}
    S=2^2\left(0.75+\frac{\pi}{16}\right)\approx 3.785398.
\end{equation*}

\section{Мониторинг приложения в JConsole}

\subsection{Регистрация и атрибуты MBean}

MBean регистрируются со следующими именами:
\begin{itemize}
    \item \texttt{com.example.lab4:type=PointStatistics};
    \item \texttt{com.example.lab4:type=Area}.
\end{itemize}

MBean \texttt{PointStatistics} предоставляет атрибуты \texttt{TotalPoints}, \texttt{HitPoints}, \texttt{MissPoints} и операцию \texttt{reset()}. MBean \texttt{Area} предоставляет атрибуты \texttt{Radius} и \texttt{Area}.

\subsection{Проверка JMX-уведомления}

Для проверки уведомления были выполнены следующие действия:
\begin{enumerate}
    \item в JConsole открыт MBean \texttt{com.example.lab4:type=PointStatistics};
    \item до добавления десятой точки проверено отсутствие уведомления;
    \item в веб-приложении добавлены точки до общего количества 10;
    \item в JConsole проверено появление уведомления типа \texttt{com.example.lab4.point.totalMultipleOfTen}.
\end{enumerate}

В контрольном запуске после десяти точек получены значения \texttt{TotalPoints=10}, \texttt{HitPoints=7}, \texttt{MissPoints=3}. Уведомление отправлено один раз — в момент перехода счётчика с 9 на 10.

\section{Мониторинг и профилирование в VisualVM}

В VisualVM был выбран процесс Java-сервера с развёрнутым приложением. После добавления точек изменялись атрибуты \texttt{TotalPoints}, \texttt{MissPoints} и \texttt{Area}. При выборе другого радиуса изменялся атрибут \texttt{Area}.

\reportfigure{screenshots/visualvm-mbeans-graph.png}{График изменения показателей MBean во времени в VisualVM}

Для анализа памяти использовался раздел Sampler/Profiler. В исходной реализации список результатов хранится в объекте с областью видимости \texttt{SessionScoped} и при каждой проверке пополняется новым объектом \texttt{CheckResult}. Поэтому при большом количестве запросов размер списка и количество удерживаемых объектов растут.

\reportfigure{screenshots/visualvm-memory-before.png}{Результат анализа памяти до исправления}

В качестве проблемы производительности рассматривается не само сохранение результата в базе данных, а неограниченное накопление всех результатов в сессионном списке. Для устранения проблемы следует ограничить размер отображаемой истории либо заменить полную загрузку на постраничную выборку из базы данных. После внесения исправления необходимо повторить профилирование и приложить результат сравнения.

\reportfigure{screenshots/visualvm-memory-after.png}{Результат анализа памяти после исправления}

\section{Локализация и устранение проблемы}

\subsection{Алгоритм локализации}

Для воспроизведения поиска проблемы выполняются следующие действия:
\begin{enumerate}
    \item запустить приложение и подключиться к его JVM в VisualVM;
    \item открыть Sampler или Profiler и выполнить снимок распределения памяти;
    \item зафиксировать классы, занимающие наибольший объём памяти;
    \item выполнить большое количество проверок точек;
    \item повторить снимок и сравнить количество объектов и занимаемый ими объём;
    \item проверить ссылки на удерживаемые объекты и найти коллекцию, которая продолжает расти;
    \item ограничить историю результатов или реализовать пагинацию;
    \item повторить измерение и убедиться, что рост памяти устранён или ограничен.
\end{enumerate}

Наиболее вероятным источником роста памяти является \texttt{java.util.ArrayList}, используемый полем \texttt{results} класса \texttt{AreaCheckBean}, и объекты \texttt{com.example.lab3.model.CheckResult}, добавляемые в этот список.

Отдельно предусмотрена очистка MBean при остановке приложения. В \texttt{MonitoringRegistry} перед регистрацией проверяется наличие объекта с тем же именем, а \texttt{MBeanRegistrationListener.contextDestroyed} снимает MBean с регистрации. Это предотвращает конфликт имён при повторном развёртывании приложения и удержание старого экземпляра MBean.

\section{Проверка сборки и работоспособности}

Проект собирается под Java 17. Для проверки необходимо использовать JDK 17, Maven и сервер приложений Jakarta EE, например WildFly, настроенный для работы с данным приложением и источником данных.

Минимальная последовательность проверки:
\begin{enumerate}
    \item выполнить сборку WAR-файла командой \texttt{mvn clean package};
    \item развернуть \texttt{target/lab4.war} на сервере приложений;
    \item открыть веб-приложение и добавить несколько точек;
    \item проверить регистрацию двух MBean в JConsole;
    \item добавить десятую точку и проверить уведомление;
    \item подключиться к тому же процессу в VisualVM и выполнить мониторинг и профилирование.
\end{enumerate}

Проверка исходной логики попадания выполняется тестами \texttt{AreaHitServiceTest}. Иллюстрации мониторинга сохраняются в каталоге \texttt{report/screenshots}.

\section{Вывод}

В лабораторной работе реализованы пользовательские MBean для мониторинга Java-веб-приложения. MBean \texttt{PointStatistics} считает общее количество точек и количество промахов, а также отправляет уведомление после каждой десятой точки. MBean \texttt{Area} предоставляет текущий радиус и площадь фигуры.

С помощью JConsole проверяются атрибуты разработанных MBean, JMX-уведомление и время работы JVM. С помощью VisualVM выполняются наблюдение за изменением показателей, анализ распределения памяти и локализация проблемы неограниченного накопления объектов истории проверок. После ограничения истории или реализации пагинации необходимо повторно выполнить профилирование и подтвердить устранение проблемы скриншотами.
